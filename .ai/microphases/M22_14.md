# M22.14 — Aplicar política estable de Expo Router y version pinning

**Fase propietaria:** F22 — Runtime Native con Expo

## Por qué existe
Evitar que generated apps dependan de APIs alpha o de versiones que cambian durante la implementación.

## Resultado exacto
Al cerrar esta microfase, **Aplicar política estable de Expo Router y version pinning** debe quedar integrado, persistido/exportable cuando corresponda y cubierto por pruebas. No basta con un tipo, un botón o un placeholder.

## Engine owner
`Expo Router + Expo SQLite + Drizzle + Refine Core`

## Responsabilidad ElectroCraft
Construye únicamente la semántica portable, adapter, configuración, UX y diagnostics que el engine no trae. No dupliques el motor.

## Ubicación visual
Generated Native runtime; Studio solo muestra preview/config/diagnostics.

## Ubicación de código obligatoria
- `packages/runtime-native/`
- `packages/data-native/`

## Ubicación exacta en la app
Generated Native routes; route behavior previewed in Native fixture/Preview.

## Diseño visual exacto
No Studio router editor separate from Pantallas/Routes.

## Texto visible en español
Android; iOS; Navegación; Datos locales; Sesión; Vista previa nativa.

## Ayuda contextual
Usa HelpRegistry `help.native.runtime`. Si esta microfase introduce un concepto nuevo, añade/actualiza su HelpDescriptor en español. La ayuda crítica no puede vivir solo en un tooltip.

## Precondiciones
- La microfase anterior de la fase está COMPLETADA o la dependencia está documentada como ya disponible.
- Los contratos canónicos necesarios existen.
- El engine owner está encapsulado detrás del adapter correspondiente.

## Implementación línea por línea
1. Default navigation usa Expo Router stable Stack y standard JavaScript Tabs.
2. No uses `unstable-native-tabs` como default mientras la documentación oficial lo marque alpha/unstable.
3. En SDK modernos, application code usa Expo Router APIs y no importa directamente `@react-navigation/*` salvo adapter oficialmente requerido.
4. Antes de pinning, re-verifica Expo SDK, Expo Router, React Native, Drizzle y NativeWind compatible versions.
5. Guarda tested dependency matrix en generated manifest/docs.
6. Feature-gate cualquier API experimental.
7. Upgrade tests generan una app fixture y ejecutan typecheck/prebuild.
8. Documenta fallback a Stack/JS Tabs.
9. Mapea canonical components/navigation/data/state/actions a RN/Expo adapters.
10. No reutilices DOM components.
11. Implementa Expo Router/SQLite only from portable definitions.
12. Añade accessibility and device-safe behavior.
13. Prueba runtime fixture.

## Artefactos obligatorios al cerrar
- `NATIVE_DEPENDENCY_MATRIX.md`
- `router stability test`

## Estados y errores
- Define empty/loading/error/disabled/blocked cuando tengan sentido.
- Un caso unsupported nunca se convierte silenciosamente en success.
- Diagnostics deben incluir código, ubicación, causa y acción sugerida.

## Responsive y accesibilidad si toca UI
- Desktop high-density sin overflow.
- Tablet usa Sheet/Drawer para tooling secundario.
- Mobile usa route/card/bottom-sheet, no desktop comprimido.
- Keyboard/focus-visible/aria-label.
- Alternative a DnD/gestos.

## Pruebas obligatorias
1. Unit/contract del valor Electro.
2. Integration con engine/storage real.
3. Negative/failure path.
4. Round-trip si persiste canonical data.
5. E2E si existe UI.
6. Target fixture si afecta export/native/server.
7. lint.
8. typecheck.
9. test.
10. build.

## Prohibido
- No crear subsystem paralelo.
- No persistir engine internals como modelo canónico.
- No usar mocks permanentes.

## Evidencia TRACKING

- pruebas ejecutadas;
- build/fixture;
- blockers/adaptations;
