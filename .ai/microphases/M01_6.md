# M01.6 — Documentar conventions

**Fase propietaria:** F01 — Monorepo, límites, documentación y CI

## Por qué existe
Esta microfase existe para **Documentar conventions** dentro de la responsabilidad de `F01`: crear boundaries, tooling y CI. Debe cerrar una capacidad concreta y no abrir un subsystem paralelo.

## Resultado exacto
Al cerrar esta microfase, **Documentar conventions** debe existir como capacidad real, integrada y verificable. No se acepta placeholder ni una implementación paralela al engine.

## Engine owner
`TypeScript/Vite/Vitest/Playwright/CI`

### Regla
Antes de escribir código, consulta la API pública del engine. Si ya existe la capacidad, úsala. ElectroCraft solo debe aportar canonical mapping, configuración, UX, adapter, target semantics o exportación.

## Packages/área de código
`repo root/apps/packages`

## Ubicación visual
QA/release; no crear nueva UI salvo diagnóstico necesario.


## Ubicación de código obligatoria
- `apps/studio/`
- `packages/*/`
- `.github/workflows/`
- `tooling/`

## Ubicación exacta en la app
No crea UI de producto; trabaja en monorepo/tooling/CI/docs.

## Diseño visual exacto
Sin diseño de pantalla. Si necesita output, usa consola/reporte Markdown.

## Texto visible en español
No hay labels de usuario final.

## Ayuda contextual
Usa HelpRegistry `help.architecture.repository`. Si esta microfase introduce un concepto nuevo, añade/actualiza su HelpDescriptor en español. La ayuda crítica no puede vivir solo en un tooltip.

## Precondiciones
- `M01.5` COMPLETADA.
- Engine owner disponible detrás de su adapter.
- No existen errores P0/P1 de la dependencia inmediata.
- Tests existentes están verdes antes de modificar comportamiento.

## Implementación línea por línea
1. Crea/normaliza `AGENTS.md` como entry point corto; no repitas el Prompt Maestro completo allí.
2. Mantén `.ai/README.md` con mapa documental y orden de lectura por sesión.
3. Mantén obligatoriamente: `PROMPT_MAESTRO_ELECTROCRAFT_2.md`, `MASTER_SPEC.md`, `REQUIREMENTS.md`, `RULES.md`, `MEMORY.md`, `STATE.md`, `ARCHITECTURE.md`, `DATA_MODELS.md`, `EDITOR_ENGINE.md`, `WIDGET_SYSTEM.md`, `DESIGN_SYSTEM.md`, `THEME_SYSTEM.md`, `CONTENT_ENGINE.md`, `BACKEND_BUILDER.md`, exporters, `SECURITY.md`, `ACCESSIBILITY.md`, `TEST_STRATEGY.md`, `PHASES.md`, `TRACKING.md`, `DECISIONS.md`, `BLOCKERS.md`, `CHANGELOG.md` y `HANDOFF.md`.
4. Crea `.ai/evidence/` para logs/checksums/reports reales y `.ai/templates/` para Microphase/ADR/Bug/Handoff templates.
5. `MEMORY.md` contiene solo hechos estables/decisiones vigentes; no copiar logs de progreso.
6. `STATE.md` contiene estado actual compacto; `TRACKING.md` contiene la tabla/posición de microfase; `HANDOFF.md` contiene la siguiente acción exacta.
7. `DECISIONS.md` resume ADR vigentes; ADR detallados viven en `.ai/adr/` cuando existan.
8. No cargues todos los `.md` en cada sesión: AGENTS define un minimal read set y la microfase enlaza specs adicionales.
9. Los archivos históricos/review reports no pueden competir como fuente de verdad; se mueven a history/archive o se eliminan de la spec final.
10. Añade un doc consistency test/script que valide links a phase/microphase IDs, required files y una única microfase ACTIVE.
11. Crea/modifica primero configuración de workspace/package.
12. Define boundary/public exports del paquete.
13. Añade tooling/CI antes de features dependientes.
14. Añade test de import-boundary.
15. Ejecuta pipeline completo.

## Artefactos obligatorios al cerrar
- `documento/ADR o matriz de evidencia de la microfase`
- `test/fixture que reproduce la decisión`

## Flujo de datos obligatorio
1. Usuario/Runtime produce una intención.
2. UI/hook llama al adapter o application service propietario.
3. El engine OSS ejecuta la responsabilidad que le pertenece.
4. ElectroCraft normaliza solo lo que necesita persistencia/portabilidad.
5. Storage o target adapter persiste/ejecuta.
6. Resultado tipado vuelve a UI/runtime.
7. Error/diagnostic permanece visible y reparable.

## Estados cuando apliquen
- initial;
- loading;
- ready;
- empty;
- error;
- disabled;
- saving;
- saved;
- blocked.

## Responsive si existe UI
- Desktop >=1280: patrón completo/high density.
- Laptop 1024–1279: reduce herramientas secundarias antes de reducir la región principal.
- Tablet 768–1023: tools secundarias a Sheet/Drawer.
- Mobile <768: route/card/bottom-sheet/full-height tool; nunca desktop comprimido.

## Accesibilidad
- keyboard;
- focus-visible;
- aria-label en icon-only;
- labels persistentes;
- errores no dependientes del color;
- alternativa a DnD cuando aplique;
- touch targets correctos;
- reduced motion donde corresponda.

## Pruebas obligatorias
1. Unit/contract para lógica Electro propia.
2. Integration con engine/storage real.
3. Negative/error test.
4. Persistence/round-trip si toca canonical data.
5. E2E si existe interacción de usuario.
6. Target fixture si afecta export/native/server.
7. `lint`.
8. `typecheck`.
9. `test`.
10. `build`.

## Prohibido
- reconstruir una función disponible en el engine;
- añadir subsystem/widget/model únicamente por conveniencia;
- persistir engine internals como proyecto canónico;
- usar datos hardcoded permanentes;
- declarar COMPLETADA sin evidencia.

## Evidencia que debes registrar en TRACKING
- archivos modificados;
- API/engine utilizado;
- tests exactos;
- build/fixture result;
- blockers o adaptación;
- próxima microfase exacta.
