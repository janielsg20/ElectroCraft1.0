# M20.4 — Fallback registry

**Fase propietaria:** F20 — Compatibilidad multi-target

## Por qué existe
Esta microfase existe para **Fallback registry** dentro de la responsabilidad de `F20`: analizar compatibilidad multi-target. Debe cerrar una capacidad concreta y no abrir un subsystem paralelo.

## Resultado exacto
Al cerrar esta microfase, **Fallback registry** debe existir como capacidad real, integrada y verificable. No se acepta placeholder ni una implementación paralela al engine.

## Engine owner
`Electro Capability Registry`

### Regla
Antes de escribir código, consulta la API pública del engine. Si ya existe la capacidad, úsala. ElectroCraft solo debe aportar canonical mapping, configuración, UX, adapter, target semantics o exportación.

## Implementación línea por línea
1. FallbackRegistry maps one portable capability to an explicit adaptation per target.
2. Every adaptation has target, reason, semanticImpact, userActionRequired and reversible flag.
3. Examples: Web Grid -> Native simpler layout; Table -> Native cards; unsupported native Embed -> explicit Link/WebView adaptation; WordPress component -> dynamic block.
4. LAMP and WordPress are normal target mappings, never hidden in fallback-only code.
5. A fallback is never auto-applied without being listed in Compatibility report before generation.
6. `blocked` is used when no safe semantic adaptation exists.
7. Test accepted/rejected adaptations and blocker flow.
8. Actualiza Capability/TargetDescriptor contract.
9. Analiza todos los nueve targets desde el mismo project snapshot.
10. Renderiza Compatibility/Export UI desde registries, no arrays hardcoded divergentes.
11. Bloquea Generate solo por blockers reales.
12. Prueba target parity/status/config host.
