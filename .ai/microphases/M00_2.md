# M00.2 — Auditar responsabilidades OSS

**Fase propietaria:** F00 — Auditoría de producto, OSS y POCs

## Por qué existe
Esta microfase existe para **Auditar responsabilidades OSS** dentro de la responsabilidad de `F00`: validar engines, ownership y POCs antes de construir producto. Debe cerrar una capacidad concreta y no abrir un subsystem paralelo.

## Resultado exacto
Al cerrar esta microfase, **Auditar responsabilidades OSS** debe existir como capacidad real, integrada y verificable. No se acepta placeholder ni una implementación paralela al engine.

## Engine owner
`POCs y engines oficiales`

### Regla
Antes de escribir código, consulta la API pública del engine. Si ya existe la capacidad, úsala. ElectroCraft solo debe aportar canonical mapping, configuración, UX, adapter, target semantics o exportación.

## Packages/área de código
`experiments + ADR/docs`

## Ubicación visual
QA/release; no crear nueva UI salvo diagnóstico necesario.


## Ubicación de código obligatoria
- `experiments/`
- `.ai/adr/`
- `.ai/evidence/F00/`

## Ubicación exacta en la app
No crea UI release. Trabaja en `experiments/` y documentación/fixtures de F00.

## Diseño visual exacto
Harness técnico aislado: tres regiones simples Request/Resultado/Validación cuando el POC necesite inspección. No añadir Sidebar route.

## Texto visible en español
No hay texto de release. Cualquier harness temporal se marca `POC técnico`.

## Ayuda contextual
Usa HelpRegistry `help.architecture.poc`. Si esta microfase introduce un concepto nuevo, añade/actualiza su HelpDescriptor en español. La ayuda crítica no puede vivir solo en un tooltip.

## Precondiciones
- `M00.1` COMPLETADA.
- Engine owner disponible detrás de su adapter.
- No existen errores P0/P1 de la dependencia inmediata.
- Tests existentes están verdes antes de modificar comportamiento.

## Implementación línea por línea
1. Para cada engine aprobado abre documentación/repositorio oficial vigente y registra responsabilidad, API pública, experimental/preview, licencia y target compatibility.
2. Puck: Composition, Slots, Fields, Outline, Preview, permissions, history, viewports, theming y límites de overrides; Puck AI no es la AI architecture.
3. shadcn/ui: verifica Radix como base soportada actual y su CLI/registry behavior; verifica además AI Elements seleccionados para la UI de IA y evita mezclar bases.
4. i18next/react-i18next: verifica typed translation workflow y tooling; español será fallback obligatorio.
5. PGlite/Drizzle: multi-tab Worker, persistence baseline, migrations.
6. Refine/TanStack/RHF/Zod/RQB: documenta las capacidades que prohíben CRUD/table/form/query-cache/CSV engines paralelos.
7. Rete/Tiptap/Zustand: documenta runtime/history/static-render/persistence responsibilities.
8. Gemini: verifica @google/genai, Interactions API, structured output, function calling, image generation, model catalog y credential rules.
9. Expo/Expo Router/SQLite: verifica APIs estables y features experimentales.
10. Auxiliary: Lucide/ECharts/Victory Native/FullCalendar Standard/react-native-calendars/dnd-kit; licencias y target role.
11. Actualiza ENGINE_RESPONSIBILITY_MATRIX y DEPENDENCY_BASELINE draft.
12. Elimina/reescribe cualquier microfase que reconstruya una capacidad confirmada del engine.
13. Aísla el experimento; no importes implementación de producto no aprobada.
14. Define fixture mínimo reproducible.
15. Ejecuta la API OSS real que se está evaluando.
16. Mide el gap entre OSS y semántica ElectroCraft.
17. Documenta decisión/limitación/licencia/API usada.
18. Guarda logs/artifacts en evidence.

## Artefactos obligatorios al cerrar
- `documento/ADR o matriz de evidencia de la microfase`
- `test/fixture que reproduce la decisión`
- `auth/permission adapter/service`
- `allow/deny/security tests`

## Flujo de datos obligatorio
1. Usuario/Runtime produce una intención.
2. UI/hook llama al adapter o application service propietario.
3. El engine OSS ejecuta la responsabilidad que le pertenece.
4. ElectroCraft normaliza solo lo que necesita persistencia/portabilidad.
5. Storage o target adapter persiste/ejecuta.
6. Resultado tipado vuelve a UI/runtime.
7. Error/diagnostic permanece visible y reparable.

- focus-visible;
- aria-label en icon-only;
- labels persistentes;
- errores no dependientes del color;
- alternativa a DnD cuando aplique;
- touch targets correctos;
- reduced motion donde corresponda.

## Pruebas obligatorias
1. Unit/contract para lógica Electro propia.
2. Integration con engine/storage real.
3. Negative/error test.
4. Persistence/round-trip si toca canonical data.
5. E2E si existe interacción de usuario.
6. Target fixture si afecta export/native/server.
7. `lint`.
8. `typecheck`.
9. `test`.
10. `build`.

## Prohibido
- reconstruir una función disponible en el engine;
- añadir subsystem/widget/model únicamente por conveniencia;
- persistir engine internals como proyecto canónico;
- usar datos hardcoded permanentes;
- declarar COMPLETADA sin evidencia.

- blockers o adaptación;
- próxima microfase exacta.
