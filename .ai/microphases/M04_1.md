# M04.1 — Crear schema físico estable por objetos y contenido

**Fase propietaria:** F04 — Persistencia local, proyectos y revisiones

## Por qué existe
Esta microfase existe para **Crear schema físico estable por objetos y contenido** dentro de la responsabilidad de `F04`: persistir incrementalmente y gestionar proyectos/revisiones. Debe cerrar una capacidad concreta y no abrir un subsystem paralelo.

## Resultado exacto
Al cerrar esta microfase, **Crear schema físico estable por objetos y contenido** debe existir como capacidad real, integrada y verificable. No se acepta placeholder ni una implementación paralela al engine.

## Engine owner
`PGlite/Drizzle + OPFS`

### Regla
Antes de escribir código, consulta la API pública del engine. Si ya existe la capacidad, úsala. ElectroCraft solo debe aportar canonical mapping, configuración, UX, adapter, target semantics o exportación.

## Implementación línea por línea
1. Sustituye el schema anterior basado en snapshots completos por tablas estables de objetos:
2. - `projects`;
3. - `project_objects`;
4. - `project_revisions`;
5. - `content_records`;
6. - `taxonomy_terms`;
7. - `record_terms`;
8. - `relation_edges`;
9. - `record_field_index`;
10. - `workspace_preferences`;
11. - `media_metadata`;
12. - `audit_events`;
13. - `form_drafts` opcional;
14. - tablas auth/user solo cuando el runtime/profile las necesite.
15. `project_objects` guarda cada objeto canónico de forma independiente: project settings, document, schema, query, form definition, action graph, state definition, roles, routes, theme y reusable components.
16. Columnas mínimas: `projectId`, `objectId`, `kind`, `schemaVersion`, `payload`, `checksum`, `updatedAt`.
17. `project_revisions` NO guarda una copia por cada keystroke; guarda checkpoints/manifests coherentes de versiones de `project_objects`.
18. `content_records.data` sigue siendo JSONB para fields dinámicos.
19. `record_field_index` es un índice genérico tipado para fields marcados searchable/filterable/sortable/faceted; no indexar todo.
20. Crea migrations Drizzle solo para este schema físico estable.
21. Prueba upgrades de schema físico sin depender de los Modelo de datoss del usuario.
22. Cambia primero repository/service contract.
23. Implementa Drizzle/PGlite transaction/migration.
24. Conecta use-case; UI nunca llama PGlite directamente.
25. Añade save/reopen/recovery behavior.
26. Añade migration/integration fixture.

## Flujo de datos obligatorio
1. Usuario/Runtime produce una intención.
2. UI/hook llama al adapter o application service propietario.
3. El engine OSS ejecuta la responsabilidad que le pertenece.
4. ElectroCraft normaliza solo lo que necesita persistencia/portabilidad.
5. Storage o target adapter persiste/ejecuta.
6. Resultado tipado vuelve a UI/runtime.
7. Error/diagnostic permanece visible y reparable.
