# M08.1 — Fuentes de datos y ConnectorRegistry

**Fase propietaria:** F08 — Fuentes de datos, modelos internos, registros y conectores

## Por qué existe
Un Builder de Apps No-Code necesita tratar el datos internos interno como una fuente de datos más, no como el centro de toda la arquitectura.

## Resultado exacto
Al cerrar esta microfase, **Fuentes de datos y ConnectorRegistry** existe como capacidad real, conectada a los contratos de ElectroCraft y demostrada con pruebas. No se acepta placeholder, botón decorativo ni contrato sin consumidor.

## Engine owner
`ElectroCraftDataSource contracts + ConnectorRegistry`

## Responsabilidad ElectroCraft
ElectroCraft conserva únicamente la semántica portable, la UX española, los adapters, permisos, validación, persistencia y compatibilidad multi-target. El engine OSS conserva la responsabilidad técnica para la que fue elegido.

## Ubicación de código obligatoria
- `packages/connectors/`
- `packages/data-web/`
- `packages/domain/src/data/`
- `apps/studio/src/features/data/`

## Ubicación exacta en la app
`Datos > Fuentes de datos`.

## Diseño visual exacto
Lista 300px izquierda; detalle central con Resumen/Configuración/Autenticación/Esquema/Prueba; inspector/right summary para seguridad/compatibilidad.

## Texto visible en español
Fuentes de datos; Nueva fuente; Interna; REST API; GraphQL; Probar conexión; Esquema; Credenciales; Requiere gateway.

## Ayuda contextual
Usa HelpRegistry `help.data.sources`. El título de pantalla lleva `CircleHelp`; los conceptos técnicos usan `Info` solo cuando aportan contexto real.

## Precondiciones
- Gate de entrada de la fase satisfecho.
- Contratos/engines anteriores verdes.
- No existe una implementación paralela de la misma responsabilidad.

## Implementación paso por paso
1. Define `ElectroCraftDataSourceDefinition` con id, kind, label, capability set, authRef, config, schema discovery policy y environment scope.
2. Define `DataSourceAdapter` con testConnection, listResources, getSchema, query/mutate capability contracts.
3. Define `ConnectorRegistry` de aplicación; el proyecto persiste solo IDs/config portable y refs, nunca clases del adapter.
4. Crea kinds iniciales `internal`, `rest`, `graphql`; SQL server connectors quedan en optional connector packs.
5. Define capability flags: read, create, update, delete, pagination, filtering, sort, aggregate, realtime, file, transactions.
6. Implementa pantalla Fuentes de datos con estado de conexión, capabilities y ayuda.
7. Valida que secrets sean referencias a SecretStore/Gateway y no payload de proyecto.
8. Prueba register/unregister, missing adapter, unsupported operation y round-trip.
9. Define DataSource/DataModel contract/capabilities.
10. Implementa adapter/repository behind ConnectorRegistry.
11. Resuelve secrets por SecretRef/Gateway.
12. Construye Data UI/Explorer/Model UI indicada.
13. Prueba schema/capabilities/CRUD/error/security.
