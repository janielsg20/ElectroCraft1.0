# M02.9 — Definir wrappers versionados para payloads de engines

**Fase propietaria:** F02 — Modelo canónico de App y ownership

## Por qué existe
Permitir aprovechar formatos OSS sin convertirlos en tipos opacos imposibles de migrar.

## Resultado exacto
Al cerrar esta microfase, **Definir wrappers versionados para payloads de engines** debe quedar integrado, persistido/exportable cuando corresponda y cubierto por pruebas. No basta con un tipo, un botón o un placeholder.

## Engine owner
`Electro canonical contracts + Zod boundaries`

## Responsabilidad ElectroCraft
Construye únicamente la semántica portable, adapter, configuración, UX y diagnostics que el engine no trae. No dupliques el motor.

## Ubicación visual
No inventes pantalla nueva; se valida mediante schemas/tests y diagnostics técnicos.

## Ubicación de código obligatoria
- `packages/domain/`
- `packages/application/`
- `packages/contracts/`

## Ubicación exacta en la app
No crea UI de producto; trabaja en `packages/domain`, contracts, validators, serializers y migrations.

## Diseño visual exacto
Sin pantalla. Representa ejemplos como fixtures/type tests, no como UI inventada.

## Texto visible en español
No hay labels de usuario final.

## Ayuda contextual
Usa HelpRegistry `help.architecture.models`. Si esta microfase introduce un concepto nuevo, añade/actualiza su HelpDescriptor en español. La ayuda crítica no puede vivir solo en un tooltip.

## Precondiciones
- La microfase anterior de la fase está COMPLETADA o la dependencia está documentada como ya disponible.
- Los contratos canónicos necesarios existen.
- El engine owner está encapsulado detrás del adapter correspondiente.

## Implementación línea por línea
1. Define patrón `{ engine, schemaVersion, value }` para payloads serializables de engines cuando conservar su representación sea razonable.
2. Aplica inicialmente a RQB rules y Tiptap richtext; evalúa Rete/Puck pero no serialices AppState/classes internas.
3. Cada wrapper tiene validator adapter y migration adapter.
4. Domain solo conoce el wrapper portable/JSON; engine package interpreta `value`.
5. Si un engine cambia formato, migration queda dentro del adapter del engine.
6. Compatibility Analyzer debe detectar `engine`/version no soportado.
7. Documenta qué engine payloads están permitidos y cuáles están prohibidos.
8. Define/actualiza schema TypeScript/Zod en domain/contracts.
9. Añade referencias IDs, versioning y validation.
10. Implementa serializer/migration si el shape persistido cambia.
11. Añade application-facing types sin importar engines.
12. Añade fixture round-trip y boundary test.

## Artefactos obligatorios al cerrar
- `ENGINE_PAYLOAD_POLICY.md`
- `engine payload validators/tests`

## Estados y errores
- Define empty/loading/error/disabled/blocked cuando tengan sentido.
- Un caso unsupported nunca se convierte silenciosamente en success.
- Diagnostics deben incluir código, ubicación, causa y acción sugerida.

## Responsive y accesibilidad si toca UI
- Desktop high-density sin overflow.
- Tablet usa Sheet/Drawer para tooling secundario.
- Mobile usa route/card/bottom-sheet, no desktop comprimido.
- Keyboard/focus-visible/aria-label.
- Alternative a DnD/gestos.

## Pruebas obligatorias
1. Unit/contract del valor Electro.
2. Integration con engine/storage real.
3. Negative/failure path.
4. Round-trip si persiste canonical data.
5. E2E si existe UI.
6. Target fixture si afecta export/native/server.
7. lint.
8. typecheck.
9. test.
10. build.

## Prohibido
- No crear subsystem paralelo.
- No persistir engine internals como modelo canónico.
- No usar mocks permanentes.
