# M08.8 — Modelos de datos y Field Registry

**Fase propietaria:** F08 — Fuentes de datos, modelos internos, registros y conectores

## Por qué existe
Esta microfase existe para **Modelo de datos y Field Registry** dentro de la responsabilidad de `F08`: modelar datos internos/workflow/indexes sin DDL dinámico. Debe cerrar una capacidad concreta y no abrir un subsystem paralelo.

## Resultado exacto
Al cerrar esta microfase, **Modelo de datos y Field Registry** debe existir como capacidad real, integrada y verificable. No se acepta placeholder ni una implementación paralela al engine.

## Engine owner
`PGlite generic content store`

### Regla
Antes de escribir código, consulta la API pública del engine. Si ya existe la capacidad, úsala. ElectroCraft solo debe aportar canonical mapping, configuración, UX, adapter, target semantics o exportación.

## Precondiciones
- Gate de entrada de `F08` satisfecho.
- Engine owner disponible detrás de su adapter.
- No existen errores P0/P1 de la dependencia inmediata.
- Tests existentes están verdes antes de modificar comportamiento.

## Implementación línea por línea
1. Define `ElectroCraftDataModel` como tipo lógico de registros internos; sustituye el concepto central de Modelo de datos.
2. Identity: id, nombre singular/plural, descripción, icono, público/interno/singleton, menu visibility y capability refs.
3. FieldRegistry define type/label/key/help/default/required/validation/options/conditions/permissions/indexing.
4. Tipos mínimos: text, textarea, richtext, number, currency, email, phone, URL, date/time/datetime, color, select, radio, checkbox, switch, image, gallery, file, map, relation, user, taxonomy, group, repeater, calculated, conditional.
5. `storageHint` sigue siendo metadata para compilers de targets como LAMP/WordPress, no DDL dinámico del Studio.
6. Model UI usa filas compactas expandibles y Progressive Disclosure.
7. Rename/delete Field muestra usage/data impact.
8. Prueba todos los field families y schema round-trip.
9. Define DataSource/DataModel contract/capabilities.
10. Implementa adapter/repository behind ConnectorRegistry.
11. Resuelve secrets por SecretRef/Gateway.
12. Construye Data UI/Explorer/Model UI indicada.
13. Prueba schema/capabilities/CRUD/error/security.

## Flujo de datos obligatorio
1. Usuario/Runtime produce una intención.
2. UI/hook llama al adapter o application service propietario.
3. El engine OSS ejecuta la responsabilidad que le pertenece.
4. ElectroCraft normaliza solo lo que necesita persistencia/portabilidad.
5. Storage o target adapter persiste/ejecuta.
6. Resultado tipado vuelve a UI/runtime.
7. Error/diagnostic permanece visible y reparable.
