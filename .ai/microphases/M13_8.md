# M13.8 — Definir Email y Webhook como providers opcionales

**Fase propietaria:** F13 — Acciones, workflows y automatizaciones

## Por qué existe
Permitir acciones profesionales sin convertir servicios externos en requisitos del core local.

## Resultado exacto
Al cerrar esta microfase, **Definir Email y Webhook como providers opcionales** debe quedar integrado, persistido/exportable cuando corresponda y cubierto por pruebas. No basta con un tipo, un botón o un placeholder.

## Engine owner
`Rete + rete-engine + rete-history-plugin + HTTP providers`

## Responsabilidad ElectroCraft
Construye únicamente la semántica portable, adapter, configuración, UX y diagnostics que el engine no trae. No dupliques el motor.

## Implementación línea por línea
1. Define `EmailProviderPort` y `Webhook/HTTP` action sobre el Provider Registry.
2. Local/Web sin email provider configurado muestra capability/configuration diagnostic; no simula envío.
3. LAMP adapter puede usar mail transport configurado; WordPress adapter usa APIs de mail del target; provider SaaS sigue opcional.
4. Webhook usa HTTP provider con method/url/headers/body mapping y secret refs.
5. Retry/timeout/idempotency policy explícita para automations.
6. Secrets se referencian por key y nunca se serializan en project/export frontend.
7. Form Action puede usar estos providers después de validation/record commit según graph order.
8. Prueba no-provider, success mock adapter, timeout y secret-redaction.
9. Actualiza ActionGraph/node definition.
10. Mapea a Rete editor/runtime sin persistir classes.
11. Implementa node service/provider adapter.
12. Define target compiler semantics.
13. Prueba graph/history/runtime/loop/error.
