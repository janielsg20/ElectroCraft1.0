# M02.8 — Clasificar ownership: Project Objects vs Registries vs Content Entities

**Fase propietaria:** F02 — Modelo canónico de App y ownership

## Por qué existe
Evitar que el proyecto serialice registries globales, entidades runtime o definitions duplicadas.

## Resultado exacto
Al cerrar esta microfase, **Clasificar ownership: Project Objects vs Registries vs Content Entities** debe quedar integrado, persistido/exportable cuando corresponda y cubierto por pruebas. No basta con un tipo, un botón o un placeholder.

## Engine owner
`Electro canonical contracts + Zod boundaries`

## Responsabilidad ElectroCraft
Construye únicamente la semántica portable, adapter, configuración, UX y diagnostics que el engine no trae. No dupliques el motor.

## Ubicación visual
No inventes pantalla nueva; se valida mediante schemas/tests y diagnostics técnicos.

## Ubicación de código obligatoria
- `packages/domain/`
- `packages/application/`
- `packages/contracts/`

## Ubicación exacta en la app
No crea UI de producto; trabaja en `packages/domain`, contracts, validators, serializers y migrations.

## Diseño visual exacto
Sin pantalla. Representa ejemplos como fixtures/type tests, no como UI inventada.

## Texto visible en español
No hay labels de usuario final.

## Ayuda contextual
Usa HelpRegistry `help.architecture.models`. Si esta microfase introduce un concepto nuevo, añade/actualiza su HelpDescriptor en español. La ayuda crítica no puede vivir solo en un tooltip.

## Precondiciones
- La microfase anterior de la fase está COMPLETADA o la dependencia está documentada como ya disponible.
- Los contratos canónicos necesarios existen.
- El engine owner está encapsulado detrás del adapter correspondiente.

## Implementación línea por línea
1. Escribe `MODEL_OWNERSHIP.md` con tres categorías: Project Objects persistentes; registries de aplicación; content/runtime entities.
2. Project Objects: ProjectDefinition, Document, Schema, QueryDefinition, FormDefinition, ActionGraph, StateDefinition, Roles/Policies, Routes, Theme/DesignSystem, project-specific reusable components.
3. Registries: ComponentDefinition, FieldType, ActionNode, Provider, PlatformCapability y core Blueprint catalog; se versionan con la app y no se copian completos a cada proyecto.
4. Content entities: records, terms, relation edges, media metadata, users/profile data, audit events; viven en storage y se referencian por IDs.
5. Para cada tipo, define serializer owner, migration owner y exporter access pattern.
6. Actualiza ElectroCraftExportIR para leer Project Objects + required content data sin convertir el ProjectDefinition en un blob gigante.
7. Crea architecture test/fixture que falle si un core registry entero aparece serializado dentro de un proyecto.
8. Define/actualiza schema TypeScript/Zod en domain/contracts.
9. Añade referencias IDs, versioning y validation.
10. Implementa serializer/migration si el shape persistido cambia.
11. Añade application-facing types sin importar engines.
12. Añade fixture round-trip y boundary test.
