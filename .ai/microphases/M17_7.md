# M17.7 — Crear Professional Capability Packs sin nuevos engines

**Fase propietaria:** F17 — Extensiones, Kits de App y plantillas de proyecto

## Por qué existe
Preservar el catálogo profesional del Prompt Maestro como configuración y adapters, no como subsistemas duplicados.

## Resultado exacto
Al cerrar esta microfase, **Crear Professional Capability Packs sin nuevos engines** debe quedar integrado, persistido/exportable cuando corresponda y cubierto por pruebas. No basta con un tipo, un botón o un placeholder.

## Engine owner
`BlueprintInstaller + existing core engines`

## Responsabilidad ElectroCraft
Construye únicamente la semántica portable, adapter, configuración, UX y diagnostics que el engine no trae. No dupliques el motor.

## Ubicación visual
New Project Wizard / Project Kits catalog.

## Ubicación de código obligatoria
- `packages/extensions/`
- `packages/app-templates/`
- `apps/studio/src/features/extensions/`

## Ubicación exacta en la app
No direct user screen; `Compatibilidad`/Help may consume matrix. Developer documentation/evidence owns truth.

## Diseño visual exacto
No extra dashboard just for matrix.

## Texto visible en español
Extensiones; Instaladas; Disponibles; Borradores; Proyecto preconfigurado; Kit de proyecto; Instalar; Permisos; Compatibilidad.

## Ayuda contextual
Usa HelpRegistry `help.extensions`. Si esta microfase introduce un concepto nuevo, añade/actualiza su HelpDescriptor en español. La ayuda crítica no puede vivir solo en un tooltip.

## Precondiciones
- La microfase anterior de la fase está COMPLETADA o la dependencia está documentada como ya disponible.
- Los contratos canónicos necesarios existen.
- El engine owner está encapsulado detrás del adapter correspondiente.

## Implementación línea por línea
1. Genera `PROFESSIONAL_CAPABILITY_GAP_MATRIX.md` como fuente de verdad de cobertura del catálogo profesional del Prompt Maestro.
2. Para cada capability registra: `capabilityId`, nombre Electro, referencia conceptual, owner phase/microphase, implementation class, maturity, target coverage y evidence IDs.
3. `implementation class` usa: Core, Preset/Block, Target Adapter, Optional Provider o Post-Core.
4. `maturity` usa exactamente: `Demo interactiva`, `Modelado portable`, `Implementado`, `Planificado`. No presentes Modelado portable como función runtime terminada.
5. Incluye datos internos workflow/revisions/options/profiles/data stores, advanced fields, relations, listings/dynamic tags, queries multifuente/cache, form calculations/frontend edit, facets/chips/indexer, backend quick edit/bulk/saved views/Kanban/Calendar/dashboard, automation/audit, imports/exports, Theme/Project Kits y target exporters.
6. Incluye el catálogo visible de Layout/Content/Navigation/Social/Commerce del `PALETTE_CATALOG_MATRIX.md`; un Block/Preset puede satisfacer una capability sin nueva clase runtime.
7. Cada capability `Implementado` debe apuntar a test/evidence verificable; si no existe evidencia, bájala a Demo/Modelado/Planificado.
8. `PROFESSIONAL_CAPABILITY_MATRIX.md` puede ser el resumen humano; `GAP_MATRIX` es la tabla auditable.
9. Cero capabilities del Prompt original pueden quedar sin owner o sin motivo explícito de Post-Core.
10. Añade validation script/test que falle por duplicate owner, missing owner o `Implementado` sin evidence.
11. Valida manifest/version/dependencies/permissions.
12. Instala artifacts mediante services existentes.
13. No crees runtime de plugin paralelo.
14. Conecta Catalog/Install/Conflict UI.
15. Prueba install/upgrade/uninstall/code quarantine.

## Artefactos obligatorios al cerrar
- `PROFESSIONAL_CAPABILITY_MATRIX.md`
- `capability ownership validation`

## Estados y errores
- Define empty/loading/error/disabled/blocked cuando tengan sentido.
- Un caso unsupported nunca se convierte silenciosamente en success.
- Diagnostics deben incluir código, ubicación, causa y acción sugerida.

## Responsive y accesibilidad si toca UI
- Desktop high-density sin overflow.
- Tablet usa Sheet/Drawer para tooling secundario.
- Mobile usa route/card/bottom-sheet, no desktop comprimido.
- Keyboard/focus-visible/aria-label.
- Alternative a DnD/gestos.

## Pruebas obligatorias
1. Unit/contract del valor Electro.
2. Integration con engine/storage real.
3. Negative/failure path.
4. Round-trip si persiste canonical data.
5. E2E si existe UI.
6. Target fixture si afecta export/native/server.
7. lint.
8. typecheck.
9. test.
10. build.

## Prohibido
- No crear subsystem paralelo.
- No persistir engine internals como modelo canónico.
- No usar mocks permanentes.

- build/fixture;
- blockers/adaptations;
- siguiente microfase.
