# M27.7 — Auditar APIs experimentales y fijar dependency baseline

**Fase propietaria:** F27 — Hardening, paridad de exportación y release

## Por qué existe
Evitar que el core dependa inadvertidamente de APIs alpha/experimental de los engines OSS.

## Resultado exacto
Al cerrar esta microfase, **Auditar APIs experimentales y fijar dependency baseline** debe quedar integrado, persistido/exportable cuando corresponda y cubierto por pruebas. No basta con un tipo, un botón o un placeholder.

## Engine owner
`toolchain audits/security/a11y/performance`

## Responsabilidad ElectroCraft
Construye únicamente la semántica portable, adapter, configuración, UX y diagnostics que el engine no trae. No dupliques el motor.

## Ubicación visual
Settings/quality reports/Deploy boundaries.

## Ubicación de código obligatoria
- `packages/testing/`
- `fixtures/canonical-app/`
- `.ai/evidence/F27/`
- `.ai/`

## Ubicación exacta en la app
No user UI; dependency baseline/evidence.

## Diseño visual exacto
Report only; blockers may surface in final release gate.

## Texto visible en español
Seguridad; Accesibilidad; Rendimiento; Dependencias; Requiere actualización; Desplegar.

## Ayuda contextual
Usa HelpRegistry `help.quality`. Si esta microfase introduce un concepto nuevo, añade/actualiza su HelpDescriptor en español. La ayuda crítica no puede vivir solo en un tooltip.

## Precondiciones
- La microfase anterior de la fase está COMPLETADA o la dependencia está documentada como ya disponible.
- Los contratos canónicos necesarios existen.
- El engine owner está encapsulado detrás del adapter correspondiente.

## Implementación línea por línea
1. Revisa release notes/docs oficiales de Puck, shadcn/ui Radix, AI Elements, i18next, Refine, Rete, RQB, PGlite, Drizzle, AI SDK/@ai-sdk-google, Expo/Router, Capacitor, Slim, WordPress APIs, Zustand, Tiptap, NativeWind y auxiliary UI engines.
2. Genera `DEPENDENCY_BASELINE.md` con versión probada, licencia, APIs críticas usadas y stability status.
3. Marca Puck overrides/plugins experimentales, Expo Native Tabs u otras APIs alpha; ninguna puede ser release-critical sin fallback.
4. Revalida cualquier Puck AI feature solo como posible integración interna; no debe competir con ElectroCraft AI SDK/Gemini ni convertirse en dependencia del core.
5. Ejecuta dependency audit/licensing and build fixtures después de pinning.
6. No copies exact version from old docs without rechecking package release compatibility.
7. Define upgrade cadence and adapter contract tests.
8. Block release if a critical path depends exclusively on an unstable API.
9. Ejecuta la fixture canónica, no una demo alternativa.
10. Corre gate específico solicitado sobre todo el sistema.
11. Reabre owner microphase ante gap P0/P1.
12. Actualiza matrices/evidence con paths reales.
13. No compenses un target fallido con otro.
14. Cierra release solo con evidencia coherente.
