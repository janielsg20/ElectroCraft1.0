# M11.3 — Persistence adapters

**Fase propietaria:** F11 — Estado, variables y entorno

## Por qué existe
Esta microfase existe para **Persistence adapters** dentro de la responsabilidad de `F11`: resolver runtime state con Zustand. Debe cerrar una capacidad concreta y no abrir un subsystem paralelo.

## Resultado exacto
Al cerrar esta microfase, **Persistence adapters** debe existir como capacidad real, integrada y verificable. No se acepta placeholder ni una implementación paralela al engine.

## Engine owner
`Zustand`

### Regla
Antes de escribir código, consulta la API pública del engine. Si ya existe la capacidad, úsala. ElectroCraft solo debe aportar canonical mapping, configuración, UX, adapter, target semantics o exportación.

- `M11.2` COMPLETADA.

## Implementación línea por línea
1. Usa Zustand `persist` middleware únicamente para StateDefinitions marcadas persistent/session según policy.
2. Proporciona Electro StorageAdapter por target; no acoples StateDefinition a localStorage/AsyncStorage.
3. El storage persistido tiene `version`, namespace/project/runtime ID y solo el subset definido por `partialize`.
4. Antes de aceptar datos rehidratados, valida/deserializa con Zod/schema generated from ElectroCraftStateDefinition; el helper JSON default de Zustand no es suficiente para datos corruptos/tampered.
5. Usa `migrate` para cambios de versión y `skipHydration`/rehydrate manual cuando Auth/DB bootstrap necesite controlar el orden.
6. Sensitive state nunca usa storage inseguro; Native puede mapear a SecureStore solo para valores pequeños apropiados.
7. Un valor inválido se descarta/repara con diagnostic, no se castea silenciosamente al tipo TypeScript.
8. Testea migration, corrupted payload, async hydration y logout/session clearing.
9. Actualiza StateDefinition.
10. Implementa Zustand adapter/persistence only for JS runtimes.
11. Conecta Bindings/Actions/Debug.
12. Declara target scope mappings.
13. Prueba hydrate/migrate/sensitive state.

1. Usuario/Runtime produce una intención.
2. UI/hook llama al adapter o application service propietario.
3. El engine OSS ejecuta la responsabilidad que le pertenece.
4. ElectroCraft normaliza solo lo que necesita persistencia/portabilidad.
5. Storage o target adapter persiste/ejecuta.
6. Resultado tipado vuelve a UI/runtime.
7. Error/diagnostic permanece visible y reparable.
